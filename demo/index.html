    Scenario 2 — Replay Attack

    An attacker captures a valid WPT from the wire and attempts to reuse it. The jti nonce store on Workload B detects the replay and rejects the request, even though the token signature is cryptographically valid.

    Threat: Network interception + replay Mitigated by jti nonce store
    ATTACK FLOW
    1
    Setup & issue a valid WIT+WPT
    2
    First request — legitimate (should succeed)
    jti recorded in nonce store
    3
    Attacker replays the same WPT
    Same jti → rejected by nonce store

    The attacker reuses the intercepted WPT verbatim. The signature is still valid, but the jti has already been seen — Workload B rejects it.

    Scenario 3 — Token Tampering

    An attacker intercepts a WIT and modifies the payload (e.g., changes the sub to escalate privileges). The ECDSA signature verification instantly detects the modification.

    Threat: Payload forgery / privilege escalation Mitigated by ES256 signature
    ATTACK FLOW — payload tampering
    1
    Issue a legitimate WIT
    2
    Tamper: replace the payload
    Modifies sub to an admin identity, keeps original signature

    The attacker base64-decodes the JWT payload, rewrites sub to spiffe://cloud-a.example/admin, re-encodes, and splices back in. The original ECDSA signature is left unchanged.

    3
    Submit tampered token to Workload B
    ES256 verification fails — signature ≠ payload

    Scenario 4 — Selective Disclosure (SPICE Extension)

    Phase 5 adds SD-JWT support per IETF SPICE: the IdP hashes individual claims into the JWT. The Holder (Workload A) controls which values to include in each presentation — a low-trust service learns only what it needs to.

    Scenario 5 — Workload Identity Threat Model

    A structured analysis of threats to workload-to-workload authentication, mapped to WIMSE mitigations. Click a threat to see how the protocol defends against it.

    STRIDE-inspired WIMSE arch-08
    T1
    Token Replay
    Attacker reuses a captured WPT for an unauthorized request
    CRITICAL
    Attacker → Intercepts WIT + WPT on the wire (MITM, log leak, etc.)
    Attacker → Sends identical WPT to Workload B 1 second later
    Workload B → ✗ BLOCKED — jti already in nonce store Mitigated
    Mitigation

    WPT includes a jti (JWT ID) unique nonce. Workload B records every jti it sees. A reused jti is rejected before any business logic runs. WPT TTL of 5 minutes limits the replay window even without jti tracking.

    T2
    Token Forgery / Privilege Escalation
    Attacker crafts a WIT with a higher-privileged subject
    CRITICAL
    Attacker → Constructs JWT with sub=spiffe://…/admin
    Attacker → Cannot sign with IdP's private key (not possessed)
    Workload B → ✗ BLOCKED — ECDSA signature verification fails Mitigated
    Mitigation

    WITs are signed with ES256 using the IdP's EC P-256 private key. Workload B validates the signature against the IdP's published public key. Any modification to the payload or header invalidates the signature.

    T3
    WPT / WIT Binding Break
    Attacker swaps a WPT from one request onto a different WIT
    HIGH
    Attacker → Captures WPT-1 (bound to WIT-1 via wth)
    Attacker → Pairs WPT-1 with a different WIT-2 in the headers
    Workload B → ✗ BLOCKED — sha256(WIT-2) ≠ wth in WPT-1 Mitigated
    Mitigation

    The WPT's wth claim is base64url(sha256(WIT)). Workload B recomputes the hash of the presented WIT and compares — any mismatch is rejected. This makes WPT and WIT inseparable.

    T4
    Audience Confusion
    WPT issued for Service X is sent to Service Y
    HIGH
    Workload A → Issues WPT with aud=https://api.svc-x.example/data
    Attacker → Routes the same WPT to svc-y.example
    Service Y → ✗ BLOCKED — aud claim does not match request URI Mitigated
    Mitigation

    The WPT's aud claim is set to the exact target URI. The receiving service compares aud against its own request URI. A WPT for one endpoint cannot be reused at another.

    T5
    Information Disclosure via Credential Sharing
    A WIT with roles leaks RBAC data to low-trust services
    HIGH
    Workload A → Has WIT with roles=[admin, billing, reader]
    Workload A → Calls a low-trust logging service — should not reveal roles
    Workload A → ✓ SAFE — presents SD-WIT with only sub disclosed Mitigated (SPICE)
    Mitigation (Phase 5 — SPICE)

    SD-JWT selective disclosure lets the Holder present a subset of claims. Hashes of undisclosed claims remain in _sd — the Verifier cannot recover their values without the disclosure string.
